## ۱) سه قاعدهٔ حاکم بر کل برنامه

**R-1 — کوری فازی.** اجنت فقط سند فاز جاری را می‌بیند. نه نقشهٔ راه، نه گزارش ممیزی (`AUDIT-FULL-2026-11-08.fa.md`)، نه اسناد فازهای قبلی به‌عنوان «زمینه». اگر لازم شد فاز قبل را ببیند، آن فاز **بسته** شده و مرجعش فقط شواهد عددی است، نه پرامپت‌ها.

**R-2 — دروازهٔ عددی، نه دروازهٔ روایی.** هیچ فازی با «توضیح قانع‌کننده» تأیید نمی‌شود. تأیید فقط با: (الف) شرط DoD که مکانیکی سنجیده می‌شود، (ب) عددی که ناظر **خودش** دوباره اجرا کرده و همان را گرفته، (ج) دیفی که در دامنه است.

**R-3 — یک فاز = یک پرامپت خودبسنده.** پرامپت هر فاز فقط پس از تأیید فاز قبل نوشته می‌شود، چون بخشی از ورودی‌هایش باید از **واقعیتِ خروجی فاز قبل** بیاید، نه از پیش‌بینی من.

هر پرامپت فاز باید **دقیقاً** این هشت بخش را داشته باشد و بخش ۰ عیناً از فاز ۱ کپی شود (قرارداد نظارتی تغییر نمی‌کند):

|---|---|---|
| ۰ | قرارداد نظارت (نقش، دامنه، H-01…H-12، دو دروازه، قالب‌ها) | کپی بدون تغییر |
| ۱ | عنوان + صورت مسئله **بدون** اشاره به فازهای قبل/بعد | فقط «چرا این کار لازم است» |
| ۲ | محدودهٔ فایل: نوشتن/ویرایش/ممنوع (جدول) | صریح تا سطح فایل |
| ۳ | ورودی‌های یخ‌زده: کیس‌های G-1…G-4 + اعداد خط مبنای **اندازه‌گیری‌شده در فاز ۱** | هر عدد با ارجاع به `measurements.json` |
| ۴ | کمیت‌های قبل/بعد که باید اندازه‌گیری شوند | هر کدام با واحد و گذر عددی |
| ۵ | بررسی‌های انسجام C-xx | با تعریف گذر عددی |

| ۷ | DoD: ۱۰–۱۵ شرط، هر کدام با شاهد لازم | هیچ شرطی بدون شاهد |
| ۸ | مرزهای ممنوعهٔ همان فاز + «چه نکن» | تکرار عامدانه |

**آزمون پذیرش پرامپت (پیش از تحویل به اجنت):**
1. آیا می‌توان از پرامپت فهمید فاز بعد چیست؟ اگر بله ⇒ بازنویسی.
2. آیا هر شرط DoD با یک دستور یا یک بازهٔ خط سنجیدنی است؟ اگر نه ⇒ حذف یا کمّی‌سازی.
3. آیا دامنهٔ «ممنوع» شامل همهٔ جاهایی است که ممکن است اجنت خودسر وارد شود؟ اگر نه ⇒ اضافه کن.
4. آیا هیچ عددی از حافظهٔ من آمده؟ ⇒ جایگزین با «اندازه‌گیری کن».

### ۳.۱ خلاصهٔ هدف هر فاز (برای نوشتن پرامپت در آینده)

- **فاز ۴:** `nearShading` جعلی حذف؛ `iam` ثابت حذف؛ ترانسپوزیشن از مدل واقعی؛ کلیپینگ با سقف و منحنی توان؛ `calculateBifacialViewFactor` وصل؛ NOCT به کاتالوگ و به مسیر.
- **فاز ۵:** `inverterClustering` از طراحی مشتق شود (نه ثابت ۳۳۰ kW)؛ `isMpptCurrentCompliant` **بلاک** کند؛ `batteryEngine` پوشش واقعی؛ `powerplantBayEngine` با clustering یکی شود یا حذف؛ `singleDiodeModel` اصلاح یا کنار گذاشتن.
- **فاز ۶:** ثابت‌های مالی به پارامتر تبدیل شوند؛ پروفایل کشوری؛ IRR چند-ریشه با هشدار؛ LCOE با salvage؛ درت اینورتر/باتری/شوری وصل؛ تحلیل حساسیت **اجباری** روی شاخص‌بندی/تنزیل/CAPEX.
- **فاز ۷:** نواحی لبهٔ ASCE، LRFD، ACI §17 یا حذف ادعا؛ یک منبع باد؛ `OfficialReportModal` از خروجی واقعی تب سازه؛ ادعای «مبحث ۶» تعیین تکلیف شود.

## ۵) پروتکل داوری ناظر — دروازهٔ میانه

در میانه هیچ کدی را تأیید نمی‌کنم؛ **جهت و صداقت** را می‌سنجم.

1. **بازتولید دو عدد تصادفی** از بخش ۳ گزارش میانه با دستور خودش. یکی از دو عدد باید عیناً برگردد؛ اگر هیچ‌کدام برنگشت ⇒ فاز از همین‌جا رد است.
2. **آزمون پوستهٔ دامنه:** `git status --porcelain` و `git diff --stat`. اگر فایل بیرون از دامنه لمس شده ⇒ رد.
3. **آزمون «عدد به‌جای وعده»:** اگر بخش ۳ خالی یا کیفی است ⇒ `PASS-WITH-CONDITIONS` با شرط «تا پایان نیمهٔ اول، n عدد واقعی».
4. **آزمون جهت:** آیا کار انجام‌شده به شرط DoD نزدیک می‌کند یا به «کارهای جانبی» منحرف شده؟ انحراف > ۲۰٪ ⇒ توقف و بازتعریف محدوده.
5. **آزمون تشدید:** آیا تشدیدهای ثبت‌شده واقعی‌اند یا بهانه؟ بررسی می‌کنم که آیا واقعاً بیرون از دامنه بوده.
6. **علامت‌های سرخ:** «تقریباً کامل»، «باید درست باشد»، جدول بدون `file:line`، عدد بدون دستور، تعریف جدید از شرط پذیرش، تفسیر موسع از دامنه.

خروجی من یکی از سه حالت، با شمارهٔ ایراد:
```
APPROVED                    ← برو نیمهٔ دوم
PASS-WITH-CONDITIONS: [۱] [۲] …   ← شرط‌ها را انجام بده، دوباره گزارش بده
REJECTED: [۱] [۲] [۳] …      ← دلیل هر مورد + شاهد
```

### ۶.۲ سه آزمون خصمانه (Adversarial)

- **خ-۱ (حذف):** فرض کن شرط DoD-X را حذف کرده‌ای؛ آیا عدد گزارش تغییر می‌کرد؟ اگر نه، آن شرط تزئینی بوده و **من** آن را از فازهای بعد حذف می‌کنم.
- **خ-۲ (جعل):** یک عدد تصادفی را در `measurements.json` دستی تغییر بده و ببین آیا چیز دیگری می‌شکند. اگر هیچ‌چیز نشکست ⇒ شواهد به هم گره نخورده‌اند؛ آن فاز از نظر «قابل‌ممیزی بودن» ناقص است.
- **خ-۳ (بازگشت):** اگر این فاز را `git revert` کنم، آیا برای فاز بعد چیزی لازم می‌ماند؟ اگر نه ⇒ فاز بی‌اثر بوده.

### ۶.۳ برچسب و بازگشت

پس از APPROVED:
```bash
git tag remediation/phase-01-approved
```
هر فاز یک برچسب دارد ⇒ بازگشت به هر نقطه، یک دستور است. اجنت مجاز به merge به `main` نیست؛ ادغام فقط با تصمیم شما.
