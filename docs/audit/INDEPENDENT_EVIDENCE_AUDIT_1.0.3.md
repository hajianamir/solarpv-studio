# ممیزی مستقل شواهد — SolarPV Studio v1.0.3

**موضوع ممیزی:** صحت ادعاهای اعتبارسنجی، منشأ داده‌ها و حدود کاربرد مهندسی
**مبنای نسخه:** فقط commit `6d508d2f3833849d92ba30f7302d9a0fd882dcbd`
**تاریخ بررسی:** 2026-11-03
**محدودهٔ تغییرات این ممیزی:** مستندات؛ هیچ کد اجرایی یا دادهٔ خامی تغییر نکرده است.

## خلاصهٔ اجرایی

این ممیزی مستقل نشان می‌دهد که نتایج آزمون‌های داخل مخزن را نمی‌توان به‌عنوان اعتبارسنجی میدانی یا بازتولید مستقل NREL SAM گزارش کرد. به‌ویژه، آزمون موسوم به Mesa/PVDAQ در `externalValidation.ts` ورودی روزانهٔ ساختگی می‌سازد، افت اندازه‌گیری‌شدهٔ `8.45%` را به‌صورت پیش‌فرض از ثابت برنامه می‌گیرد و آن را با خروجی مدل مقایسه می‌کند؛ فایل دادهٔ خام، شناسهٔ حسگر/سامانه، روش محاسبهٔ افت یا زنجیرهٔ کالیبراسیون همراه مخزن نیست. بنابراین ادعای دقت میدانی `0.12%` **قابل‌اثبات نیست**؛ این اختلاف فقط حساب داخلی دو عدد کدشده است.

سه فایل با پسوند `.sam` در واقع manifestهای JSON هستند، نه پروژه‌های اجرایی SAM یا فایل‌های آب‌وهوایی TMY. آن‌ها مقادیر هدف را ثبت می‌کنند؛ آزمون، تطبیق خروجی Studio با هدف‌های manifest را می‌سنجد، نه اجرای مستقل SAM را. عنوان قابل دفاع: «مقایسهٔ داخلی با مقادیر ثبت‌شده در manifest».

در دادهٔ اقلیم نیز برخی فیلدها از سرویس گرفته می‌شوند، اما DNI/DHI از ضرایب ثابت GHI مشتق شده‌اند، حداقل/حداکثر دما و بارندگی در مسیرهای مشخص با مدل منطقه‌ای یا مقدار پیش‌فرض پر می‌شوند و آلبدو `0.20` ثابت است. درج نام NASA POWER، PVGIS، WMO، ASHRAE یا IEC در metadata به‌تنهایی منشأ داده یا انطباق با استاندارد را ثابت نمی‌کند.

هویت سری Jinko Tiger Neo `JKM550N-72HL4-BDV` در کد و یک برگهٔ رسمی سازنده قابل ردیابی است؛ اما مقادیر CEC/fixture موجود با مشخصات STC همان مدل دقیقاً یکی نیستند. به‌عنوان نمونه، fixture کدشده Voc/Vmp/Imp برابر `50.80 V / 41.28 V / 13.33 A` دارد، درحالی‌که برگهٔ رسمی مدل 550 W مقدار `50.27 V / 41.58 V / 13.23 A` را نشان می‌دهد. بنابراین fixture را نباید «مقادیر سازنده برای همین واریانت» نامید.

هیچ‌یک از شواهد بررسی‌شده، تأیید طراحی پروژهٔ واقعی یا انطباق کامل با مقررات برق/سازه را اثبات نمی‌کند. محاسبهٔ سایز رشته یک تابع غربالگری بر پایهٔ ورودی‌های داده‌شده است؛ انتخاب دمای طراحی، مشخصات معتبر تجهیزات، شرایط سایت و بازبینی مهندس مسئول همچنان لازم است.

## راهنمای طبقه‌بندی

- **مستقل تأییدشده:** شواهد اولیهٔ بیرون از مخزن به‌طور مستقل بررسی/بازتولید شده و نتیجهٔ همان ادعا را پشتیبانی می‌کند.
- **فقط آزمون داخلی:** آزمون/کد موجود در مخزن آن رفتار داخلی را نشان می‌دهد، نه صحت فیزیکی یا صحت دادهٔ مرجع.
- **تا حدی درست / مشروط:** بخشی از ادعا مستند است اما دامنه‌اش باید محدود شود.
- **مردود:** شواهد موجود با صورت ادعاشده ناسازگار است.
- **قابل‌اثبات نیست:** شواهد اولیهٔ لازم موجود نیست یا منبع ادعاشده قابل بازتولید نیست.

«مستقل تأییدشده» در این ممیزی فقط در جایی به کار می‌رود که منبع اولیهٔ خارجی برای همان گزاره موجود باشد؛ هیچ ادعای عملکرد میدانی محصول در این طبقه قرار نگرفت.

## ناسازگاری بازتولیدپذیر در metadata و آزمون اصلاحی پیشنهادی

در مسیر parser مربوط به PVGIS، `src/engine/dataGateway/climateDataProvider.ts:826-835` برای هر خروجی دارای irradiance غیرصفر `dataStatus: 'measured'` می‌گذارد، درحالی‌که همان object منبع را `PVGIS 5.2 SARAH-2 / ERA5` معرفی می‌کند و provenance بعضی خروجی‌ها را satellite reanalysis یا مشتق‌شده/محلی می‌نامد. علت قابل مشاهده در کد، برچسب‌گذاری ثابت/مبتنی بر `psh` است، نه منشأ سنجش زمینی. اثر بالقوه: مصرف‌کنندهٔ metadata ممکن است «measured» را به اشتباه به‌عنوان اندازه‌گیری میدانی تفسیر کند. این مورد در این تغییر فقط مستند شده و کد دست‌نخورده است.

**آزمون اصلاحی مستقل پیشنهادی پیش از هر اصلاح کد:** پاسخ fixture ثابت و مصنوعی PVGIS شامل 12 ماه و T2m معتبر را به parser بدهید؛ assert کنید مقدارهای provider/reanalysis، مشتق‌های GHI و مدل‌های محلی هرکدام provenance جدا دارند و وضعیت کلی هرگز صرفاً به دلیل `psh > 0` «اندازه‌گیری میدانی» اعلام نمی‌شود. fixture دوم با صفر GHI و fixture سوم با دمای ناقص، مسیرهای `unsizable` و fallback را بپوشانند. آزمون باید روی parser خالص اجرا شود و از سرویس زنده/اینترنت مستقل باشد؛ سپس یک integration check جداگانه فقط صحت نمایش و حفظ provenance در مصرف‌کنندهٔ UI/export را بررسی کند. این طرح هنوز اجرا نشده و نتیجهٔ آن **قابل‌اثبات نیست**.

## موارد اثبات‌نشده و لازم برای بستن شکاف‌ها

1. **Mesa/PVDAQ:** فایل خام، landing record دقیق Station 1221، شناسهٔ حسگر/سریال، محدودهٔ کالیبراسیون، timestamp و timezone، QA flags، metric definition، روزهای حذف‌شده/باران، و notebook/script مستقل برای محاسبهٔ 8.45%.
2. **SAM:** نسخه/installer قابل‌اجرا، فایل پروژهٔ واقعی SAM، hash منبع اصلی، TMY3/EPW raw data با license/citation، همهٔ ورودی‌ها و تنظیمات، خروجی SAM خام و log، و اسکریپت تطبیق مستقل؛ اهداف نباید صرفاً از همان manifest مورد آزمون اخذ شوند.
3. **اقلیم:** ثبت payload خام و request URL/parameters/time، تاریخچه و resolution dataset، تفکیک provenance در UI/export برای هر فیلد، و اعتبارسنجی در نقاط جغرافیایی مستقل. Tmin/Tmax باید از design extreme معتبر بیاید؛ DNI/DHI باید از منبع مناسب یا مدل مستندتر محاسبه شوند؛ precipitation/soiling/albedo به دادهٔ زمینهٔ واقعی نیاز دارند.
4. **Jinko:** فایل CEC/CEC/SAM library نسخه‌دار و hashشده، licensing/source metadata، روش ورود مقادیر diode-model و جداسازی آن از STC برگهٔ سازنده؛ نگهداری variant، suffix و revision دقیق.
5. **استاندارد و طراحی:** تعیین jurisdiction و edition نافذ؛ traceability بندبه‌بند به test/vector؛ دمای طراحی، string cold Voc/hot Vmp، MPPT operating/current limits، fuse, reverse-current, conductor ampacity/derating/voltage-drop, grounding, protection, structure, fire/access، inverter certificates، load/utility requirements و بررسی امضاشدهٔ مهندس مسئول. هیچ تأیید طراحی نهایی از شواهد این ممیزی صادر نمی‌شود.

## دستورات بررسی و نتایج

دستورات قابل بازتولید از ریشهٔ مخزن:

```bash
git rev-parse HEAD
git status --short
git show 6d508d2f3833849d92ba30f7302d9a0fd882dcbd:package.json | grep -n '"test:benchmark"'
grep -nE '8\.45|0\.188|PVDAQ|1055749|1\.80|1\.10' src/engine/core/benchmarks/externalValidation.ts
sed -n '1,100p' benchmarks/reference_files/README.md
sed -n '306,327p' src/engine/core/benchmarks/goldenDatasets.ts
npm run test:benchmark
git diff --check
```

نتایج در اجرای ممیزی:

- `git rev-parse HEAD` → `6d508d2f3833849d92ba30f7302d9a0fd882dcbd` (برابر SHA هدف).
- `git status --short` پیش از مستندسازی → خالی (working tree تمیز)؛ پس از اصلاح مستندات فقط READMEها و دو مستند ممیزی تغییر/افزوده شدند.
- `git show 6d508d2f3833849d92ba30f7302d9a0fd882dcbd:package.json | grep -n '"test:benchmark"'` → exit 0؛ script در خط 22 target تعریف شده است.
- الگوی grep اصلاح‌شده → exit 0 و match در target؛ مقدارها و مسیرهای مورد بررسی در `externalValidation.ts` ظاهر شدند.
- `npm run test:benchmark` → **اجرا نشد**، exit 127، `sh: 1: tsx: not found`. وابستگی نصب یا کد تغییر داده نشد.
- `git diff --check` → exit 0 برای tracked diff. فایل‌های untracked مستندات نیز به‌صورت محتوای متنی مرور شدند.
- جست‌وجوی وب برای منبع اولیه: صفحهٔ رسمی OEDI/PVDAQ و PDF رسمی Jinko پیدا شد؛ در این محیط رکورد خام Station 1221 یا فایل SAM اجرایی/منبع مستقیم DOI ادعاشده بازتولید نشد.

### دامنهٔ اثبات هر نتیجه

- Git SHA فقط هویت نسخهٔ checkout را ثابت می‌کند.
- grep/مطالعهٔ کد فقط منطق، ثابت‌ها و ساختار artifact در همان commit را نشان می‌دهد.
- اجرای موفق یک unit/benchmark داخلی، فقط assertion همان harness را برای همان ورودی‌ها ثابت می‌کند.
- اجرای ناموفق به‌دلیل نبود `tsx` هیچ نتیجه‌ای دربارهٔ pass/fail آزمون‌های کد نمی‌دهد.
- صفحهٔ PVDAQ/OEDI وجود مجموعهٔ عمومی را تأیید می‌کند؛ خودش داده/اندازه‌گیری Mesa یا عدد 8.45% را تأیید نمی‌کند.
- برگهٔ Jinko مشخصات چاپ‌شدهٔ محصول را تأیید می‌کند؛ نه صحت CEC diode-fit، عملکرد واقعی پنل یا suitability پروژه را.
