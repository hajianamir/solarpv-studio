# قرارداد بهره‌برداری سه‌حالته و شروع فاز ۳

> به‌روزرسانی وضعیت: [ادامهٔ فازهای۱–۴](OPERATING-PHASES-1-4.fa.md). توضیح load-first این سند قرارداد legacy را شرح می‌دهد؛ بهینه‌سازی/دیزل/عمر و PDF واقعی در مسیر مستقل advanced اضافه شده‌اند. نتیجهٔ Windows/Linux/WebKit موفق و گیت native Safari فایل دیسکی هنوز باز است. عبارت‌های «انجام نشده» پایین، وضعیت تحویل اولیه‌اند؛ برای snapshot فعلی به گزارش ادامه مراجعه کنید.

> توسعهٔ جدید: کنترل بهینهٔ گسسته، دیزل، برآورد عمر باتری و PDF واقعی در `docs/ADVANCED-DISPATCH-AND-PDF.fa.md` ثبت شده‌اند. تحلیل پیشرفته مستقل است؛ آزمون واقعی Windows/Safari هنوز اجرا نشده و این سند نتیجهٔ تاریخی تحویل قبلی را حفظ می‌کند.
## دامنه

از این نسخه، گردش مطالعه، پذیرش سالانه، ذخیره/بازیابی، پاکت قابل‌انتقال و گزارش برای `powerplant`، `ongrid` و `offgrid` مشترک است. حالت‌های غیرنیروگاهی به فاز دیگری موکول نمی‌شوند. baseline بدون مطالعهٔ اختیاری همچنان مستقل اجرا می‌شود. مدل‌های جدید **engineering_scenario / not_field_validated** هستند.

فاز ۲ شامل قرارداد، provenance، پایداری انتخاب، مهاجرت و مسیرهای گزارش است. شروع فاز ۳ در این تحویل، اتصال PV AC معتبر به دفتر انرژی بازه‌ای بار/شبکه/باتری است؛ تکمیل تمام فیزیک‌های ردیاب/مدار/حرارتی/شبکه یا dispatch بهینه ادعا نمی‌شود.

## ورودی

در تب اقلیم، ابتدا `Download operational context` را بگیرید. مختصات، ظرفیت DC/AC، mode، هش وابستگی فیزیکی و در حالت غیرنیروگاهی ظرفیت باتری مشخص می‌شوند. سناریوی مستقل pvlib باید همین مختصات/ظرفیت‌ها را داشته باشد؛ برنامه آن را پنهانی scale نمی‌کند. ارتفاع و timezone واقعی اجرای مدل در request ذخیره‌اند؛ descriptor اختیاری فقط یادداشت است.

ورودی نیروگاهی قبلی (StudyResult یا integrated results) همچنان پذیرفته می‌شود. برای هر سه حالت می‌توان از wrapper زیر استفاده کرد؛ برای on/off-grid این wrapper **الزامی** است:

```text
{
  schemaVersion: "operating-study-v1",
  pvResults: <خروجی معتبر کامل UTC direct یا integrated batches>,
  plan: {
    schemaVersion: "operating-dispatch-v1",
    mode: "powerplant" | "ongrid" | "offgrid",
    source: <توضیح واقعی منشأ برنامه، حداقل ۱۰ حرف>,
    intervalMinutes: <دقیقاً گام شواهد PV؛ ۱ تا ۶۰ دقیقه>,
    battery: {
      capacityKwh: <ظرفیت اسمی، مطابق context پروژه>,
      minSocFraction: <۰ تا ۱>,
      initialSocFraction: <بین حداقل SOC و ۱>,
      maxChargeKw: <حد توان ورودی AC شارژ>,
      maxDischargeKw: <حد توان خروجی AC دشارژ>,
      chargeEfficiency: <۰ تا ۱، صفر مجاز نیست>,
      dischargeEfficiency: <۰ تا ۱، صفر مجاز نیست>
    },
    records: [
      {timestamp: <ISO با Z یا offset>, loadW: <بار متوسط بازه>,
       gridAvailable: <boolean>, exportLimitW: <سقف صادرات متوسط W>}, ...
    ]
  }
}
```

این نمایش **JSON اجرایی یا دادهٔ نمونهٔ عملیاتی نیست**؛ مقادیر داخل <> باید از دادهٔ کاربر بیایند. هیچ برنامهٔ سالانه‌ای از پروفایل ۲۴ ساعت، PSH یا بار روزانه ساخته نمی‌شود. timestamp پایان بازه است، نه توان لحظه‌ای. تعداد و لحظه‌های ردیف‌ها دقیقاً با PV برابرند؛ gap، overlap، عدم انطباق cadence، مقادیر منفی/نامتناهی، mode ناسازگار و ظرفیت باتری ناسازگار رد می‌شوند. واحد بار و توان W، توان باتری kW و انرژی kWh است. حداکثر ورودی ۶۴ MiB؛ آرشیو مطالعه ۶۸ و پاکت پروژه ۷۶ MiB.

- نیروگاهی: بار محلی و ظرفیت باتری باید صفر باشند. standby/auxiliary موجود در شواهد حفظ می‌شود؛ قطع شبکه و سقف صادرات صریح‌اند.
- on-grid: وضعیت شبکه هر بازه صریح است؛ هنگام قطع، واردات/صادرات صفر و بارِ تأمین‌نشده محاسبه می‌شود. این مدل فرض می‌کند تجهیز مناسب AC-coupled/island-capable وجود دارد؛ انطباق حفاظت/انتقال/anti-islanding را تأیید نمی‌کند.
- off-grid: `gridAvailable` همهٔ بازه‌ها false؛ هیچ خرید یا فروش شبکه مجاز نیست.

## ترتیب و معادلات فاز ۳

پیاده‌سازی: `src/studies/operatingDispatch.ts`، نسخهٔ `ac-load-first-no-grid-charge-v1`.

برای هر بازه با مدت Δt برحسب ساعت، انرژی برابر W×Δt/1000 است. مصرف داخلی اینورتر/کارخانه که در شواهد به‌صورت import ثبت شده، به تقاضای محلی اضافه می‌شود؛ بار محلی `loadW` نباید قبلاً همان auxiliary را دوباره شامل شده باشد.

1. PV به تقاضا می‌رسد؛ auxiliary در تخصیص بار تأمین‌شده اولویت دارد.
2. فقط مازاد PV باتری را شارژ می‌کند: کمینهٔ مازاد، توان شارژ×Δt و فضای ذخیره/ηc.
3. کسری از باتری تأمین می‌شود: کمینهٔ کسری، توان دشارژ×Δt و انرژی بالاتر از SOCmin×ηd.
4. شبکهٔ در دسترس کسری باقیمانده را وارد و مازاد را تا سقف صادر می‌کند. هنگام قطع/جزیره، کسری unmet و مازاد curtailed است.
5. SOC با ηc و ηd جدا تغییر می‌کند؛ RTE دوباره اعمال نمی‌شود. شارژ از شبکه و دشارژ برای فروش انجام نمی‌شود.

دو معادلهٔ آزموده‌شده در هر بازه:

```text
PV + import + discharge = demand + charge + export + curtailment - unmet
stored_end = stored_start + charge - discharge - battery_loss
```

باتری AC energy-bucket است، نه مدل الکتروشیمی/حرارت/ولتاژ/عمر. بار AC است؛ این طرح برای معماری DC-coupled بدون مدل مبدل مستقل قابل تعمیم خاموش نیست. فعال بودن دیزل در طراحی baseline، به این دفتر diesel dispatch اضافه نمی‌کند؛ unmet را نباید پوشش ژنراتور فرض کرد. ظرفیت/PV/ردیاب/کابل/transformer/MPPT همان شواهد معتبر upstream را استفاده می‌کنند و تلفات دوباره اعمال نمی‌شوند.

## نگاشت مالی

- نیروگاه: انرژی فروش صادرات است؛ هزینهٔ import نیروگاه مستقل کسر می‌شود.
- on-grid: انرژی ارزش‌پذیر = صادرات + خودمصرفی منتسب به PV. نسبت خودمصرفی از دفتر استخراج می‌شود، نه درصد فرضی UI. منفعت سال اول = خودمصرفی×تعرفه خرید + صادرات×تعرفه فروش. کل import خانوار مجدداً از **منفعت افزایشی PV** کم نمی‌شود؛ این گزارش کل قبض خانوار نیست.
- off-grid: فقط انرژی محلی تأمین‌شدهٔ منتسب به PV با avoided cost ارزش‌گذاری می‌شود؛ تولید دورریخته‌شده، unmet و صادرات صفر درآمد ندارند.
- SOC اولیه انرژی بیرونی است: محافظه‌کارانه کل انرژی ذخیرهٔ اولیه از خودمصرفی ارزش‌پذیر سال کسر می‌شود؛ دفتر خام تغییر نمی‌کند. SOC نهایی گزارش می‌شود و به معنای شرط cyclic نیست.
- عمر ۲۵ سالهٔ مالی از مدل موجود با degradation اسکالر استفاده می‌کند؛ بازاجرای dispatch، تغییر نرخ خودمصرفی/تعویض باتری با aging، تعرفهٔ ساعتی و outage stochastic در سال‌های بعد هنوز پیاده نشده‌اند.

## فاز ۲: انتقال و گزارش

ذخیرهٔ محلی سبک فقط شناسهٔ مطالعه دارد. دکمهٔ دانلود پاکت پروژه اکنون در صورت انتخاب منبع، فایل `solarpv_operational_project` شامل پاکت استاندارد پروژه و **شواهد کامل بازاعتبارسنجی‌شده** می‌سازد. نبود شواهد باعث خطای export می‌شود؛ پاکت ناقص بی‌صدا صادر نمی‌شود. ورود این فایل شواهد را پیش از فعال‌سازی بازاعتبارسنجی و ذخیره می‌کند؛ context جدید باید پس از مهاجرت نیز سازگار باشد. اعتبار provider claim واردشده همچنان به user-declared تنزل می‌یابد. ذخیرهٔ شواهد و کاتالوگ دو تراکنش مستقل‌اند؛ خطای مرحلهٔ بعد می‌تواند آرشیو بی‌مرجع باقی بگذارد، اما منبع تأییدنشده را فعال نمی‌کند.

گزارش منبع‌محور اکنون پیوست ساختاریافتهٔ EPC دارد: سایت و منشأ، بارها، ماژول و اینورتر، توپولوژی آرایه، ذخیره‌ساز، حفاظت، وضعیت سازه و بی‌های MV در صورت کاربرد. این پیوست، ارزیابی مستقل طراحی/screening است و **جای شواهد انرژی سالانه یا تأیید انطباق را نمی‌گیرد**. موارد unavailable/stale به همان صورت منتقل می‌شوند. نمودار waterfall، PR و روز نمایندهٔ baseline به منبع سالانهٔ انتخاب‌شده نسبت داده نمی‌شوند. چیدمان گرافیکی گزارش قدیمی عیناً بازتولید نشده؛ پوشش دادهٔ مهندسی در پیوست ساختاریافته است.

همین منبع، دفتر سالانه، مالی و پیوست EPC در پنج مسیر HTML، DOCX، XLSX، JSON با شواهد و چاپ/PDF ارائه می‌شود. متن کاربر escape می‌شود؛ دانلودها فایل OOXML واقعی‌اند. JSON گزارش سند تحلیلی است؛ برای restore پروژه از پاکت پروژه استفاده کنید. چاپ/PDF از مرورگر است؛ خروجی renderer سیستم‌عامل هنوز آزموده نشده.

## آزمون و محدودیت پذیرش

- `test:operating:dispatch`: حساب دستی مستقل، شاهد Python Decimal بدون import محصول، موازنه در هر بازه، حساسیت راندمان/حد توان، ۱۵/۳۰/۶۰ دقیقه، outage، ظرفیت و SOC، عدم تغییر ورودی، قراردادهای نامعتبر، پذیرش سالانهٔ خروجی واقعی worker با دادهٔ **مصنوعی آزمون**، آرشیو، پاکت و نگاشت مالی هر سه mode.
- `test:operating:browser`: هر سه mode در برنامهٔ production Chromium؛ خروجی واقعی worker، پذیرش plan، مالی، گزارش JSON، readback DOCX با unzip، XLSX با ExcelJS، HTML و سند چاپ؛ پاک‌کردن شواهد IndexedDB و restore همان منبع از پاکت تک‌فایلی.
- Windows/Safari، quota واقعی، CI روی commit دقیق و اعتبارسنجی میدانی در این بسته انجام نشده‌اند؛ آزمون الگوریتم و قرارداد، شاهد دقت تجربی نیست.

ادامهٔ فاز ۳: آزمون‌های مستقل عمیق‌تر شبکهٔ متعادل، ردیاب/سایه/مدار و اتصال حرارتی به جریان انرژی، توان/حفاظت جزیره‌سازی و مدل topology-specific باتری برای **هر سه mode**. این ادامه نباید baseline نامرتبط را وابسته به دادهٔ پژوهشی کند.
